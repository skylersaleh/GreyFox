GREYFOX Instruction Set Architecture

**Overview**

Features:
    - 64bit integer and IEEE floating point
    - 32 General Purpose Registers + 4 Special Purpose Registers
    - atomics
    - supervisor calls
    - virtualization
    - software breakpoints
    - Coprocessor interface for Vector, Matrix, RT, Texture, AI, String Ops, DMA, encryption, etc. cores
    - C++ compliant memory model (HW maintains LD/ST logical ordering, HW cache coherency)
    - FP Special Functions (cos/sin/tan, sqrt, rsqrt, rcp)
    - 56bit PA/VA

Registers:
    i0-i15 Integer General Purpose Registers (uint64_t/int64_t)
    f0-f15 Floating Point General Purpose Registers (double)
    PC Program Counter (uint64_t), bit 0 is always 0
    SP Stack Pointer (uint64_t)
    LR Link Register (used to hide branch latency) (uint64_t)
    FP Frame Pointer (uint64_t)
    **RESERVED** OFLOW Overflow Flag (bool)
    **RESERVED** FPMODE uint8_t (floating point mode) [1:0 MODE [0: RNE 1: RTZ 2: R+Inf 3: R-Inf]] [2 flush denorms]

General Notes:
    - Instructions that do not assign PC in their definition advance PC by 2 bytes. When PC is referenced in an instruction definition, it starts out as pointing to the first byte of the instruction. 
    - Advancing PC by zero does not increment the PC (ie. branch_relative #0). So, it will cause the program to loop infinitely over the instruction. 
    - Reserved instruction classes/registers are subject to large changes based on compiler driven testing. 

16b Fixed width instruction encoding for each instruction class:

    Short Branch Class:  [ 11:0 branch offset][15:12 op [Value 0xF]]
    Three Operand Class: [ 3:0 A  ] [ 7:4 B ] [ 11:8 C ] [ 15:12 op [Values 0xC-0xE]]
    Two Operand Class:   [ 3:0 A  ] [ 7:4 B ] [ 15:8 op [Values 0x10-0xBF]] 
    One Operand Class:   [ 3:0 A  ] [ 15:4 op2 [ Values 0x010-0x0FF]] 
    No operand Class:    [ 15:0 op2 [ Values 0x0000-0x00FF]] 

    All instructions are 2B aligned
    Total Opcode Space = 4 + 159+ 239 + 256 = 658 opcodes

    Compare Ops [0x9XXX-0xCXXX]
        Compare ops may come with an additional immediate called an extended compare command that can issue a branch, call, or return based
        on the result of the comparison operation. An assembly mnemonic for a compare instruction is contructed by combining the comparison 
        operation performed and the name of the operation named by th extended command.
        So, for example. 
            eq.f A, B will compute A = A == B
            less.i64.branch_rel_imm.i16 A, B, -100  will compute   if(A<B)PC+=-100 
            equal_zero.call_rel.i32 A, B, 0x32404885 will compute  if(A==0)call_rel(0x32404885);

        Bits [15:12] describe the size of the data for the extended compare command (treated as an immediate in the instruction stream).
            9XXX no extended branch/move command A = A cmp B. 
            AXXX XXXX 2 Byte extended branch/move command after compare instruction bytes
                AXXX 0000 "return"                           if(A cmp B){PC = LR; SP=FP-16; LR=*(uint64_t*)(SP); FP=*(uint64_t*)(SP+8);}else{ PC+=4;}
                AXXX 0001 - AXXX 7FFF "call_rel_imm.i16"     if(A cmp B){*(uint64_t*)(SP)=LR; *(uint64_t*)(SP+8)=FP; LR=PC+4; SP+=16; FP=SP;  PC +=(int16_t)(imm[14:0]*2);}else{ PC+=4;}
                AXXX 8000 "svc_return"                       if(A cmp B){svc_return;}else{ PC+=4;}
                AXXX 8001 - AXXX FFFF "branch_rel_imm.i16"   if(A cmp B){PC +=(int16_t)(imm[14:0]*2);}else{PC+=4;}
            BXXX XXXX XXXX 4 Byte extended branch/move command after compare instruction bytes
                BXXX 0000 0000 "hvc_return"                            if(A cmp B){hvc_return;}else{PC+=6;}
                BXXX 0000 0001 - BXXX 7FFF FFFF "call_rel_imm.i32"     if(A cmp B){*(uint64_t*)(SP)=LR; *(uint64_t*)(SP+8)=FP; LR=PC+6; SP+=16; FP=SP; PC +=(int32_t)(imm[30:0]*2);}else{PC+=6;}
                BXXX 8000 0000 unused
                BXXX 8000 0001 - BXXX FFFF FFFF "branch_rel_imm.i32"   if(A cmp B){PC +=(int32_t)(imm[30:0]*2);}else{PC+=6;}
            CXXX XXXX XXXX XXXX XXXX 8 Byte extended branch/move command after compare instruction bytes
                CXXX 0000 0000 0000 0000 unused

Application Binary Interface (ABI):

    Datatypes:
        In general, GreyFox stores/processes its integer types in 2's complement, its floating pointer types in IEEE-754R floating point, and supports 56 bit VA/PA addresses. 
        C language datatypes map to the following: 
            byte:       8 bits
            char:       8 bits,  signed by default, signed numbers are 2's complement encoded
            short:      16 bits, signed by default, signed numbers are 2's complement encoded
            int:        32 bits, signed by default, signed numbers are 2's complement encoded
            long:       32 bits, signed by default, signed numbers are 2's complement encoded
            long long:  64 bits, signed by default, signed numbers are 2's complement encoded
            half:       16 bits, IEEE-754R floating point binary16 (1s, 5e,  10f)
            float:      32 bits, IEEE-754R floating point binary32 (1s, 8e,  23f)
            double:     64 bits, IEEE-754R floating point binary64 (1s, 11e, 52f)
            pointer:    64 bits  (only bottom 56 bits used by HW, top 8 bits ignored)

        Unaligned loads/stores are supported, but may incur a performance penalty of the cost of two memory loads/stores.
        Unaligned atomic operations are not supported. 
        To avoid performance penalties and allow atomic operation, it is recommended to keep the following alignments:
            8-bit types: align to  1 byte
            16-bit types: align to 2 bytes
            32-bit types: align to 4 bytes
            64-bit types: align to 8 bytes
            structure/union types == 1 byte:    align to 1 bytes
            structure/union types == 2 byte:    align to 2 bytes
            structure/union types == 3-4 bytes: align to 4 bytes
            structure/union types > 4 bytes:    align to 8 bytes
            arrays: same alignment as the element type of the array
        
        Unpacked structures (default):
            - Store members in order
            - Pad each member to the recommended alignment above
            - If the structure is 3 bytes in size, pad to 4 bytes. 
            - If the structure is > 4 bytes in size, pad to a multiple of 8 bytes
        
        Packed structures:
            - Store members in order
            - No padding is applied (not even to maintain alignment)  
        
        Unpacked unions (default):
            - Members are aliased, each stored at the first byte of the union
            - The union is sized to the largest member
            - If the union is 3 bytes in size, pad to 4 bytes. 
            - If the union is > 4 bytes in size, pad to a multiple of 8 bytes
        
        Packed unions:
            - Members are aliased, each stored at the first byte of the union
            - The union is sized to the largest member
            - No padding is applied

        Arrays:
            - The pointer points to element 0
            - Arrays are densly packed, with no padding (not even to maintain alignment)
            - Elements are stored at ascending memory locations (ie. &array[0] +sizeof(array[0]) == &array[1])
        
        Function Pointers:
            - Function pointers are pointers to the start of the first instruction of the functions code sequence. 

        Calling Convention:
            Caller Saved Registers:
                Caller Saved Registers (sometimes referred to as volatile) do not preserve their value across function calls.
                They can be used by the Callee for arbitrary computation without saving/restoring them.
                - i0,i1,i2,i3,i4,i5,i6,i7
                - f0,f1,f2,f3,f4,f5,f6,f7
                - **RESERVED** FPMODE
            Callee Saved Registers:
                Callee Saved Registers (sometimes referred to as non-volatile) do preserve their value across function calls.
                They can be used by the Callee for arbitrary computation but the callee must restore them to their original values before returning to the caller. 
                - i8,i9,i10,i11,i12,i13,i14,i15
                - f8,f9,f10,f11,f12,f13,f14,f15
                - FP, SP, LR, PC (HW managed by call/ret instructions)
            Function Call Arguments and Return Data: 
                Argument Lists
                    - Function call arguments and return results are passed through argument lists. 
                    - Integral, Floating Point, Pointer, and POD structures less than or equal to the register word size can be passed directly in the argument list. 
                    - Non-POD structures, arrays, and POD structures larger than the word size are stored in memory allocated/owned by the caller and a pointer to the structure is stored in the argument list instead (even for return data).
                    - Arguments are passed in the order that they appear in the function call definition
                    - The outputs of in/out parameters overwrite the input data and are accessible by the caller after the callee returns. 
                    - The first 7 non floating point elements and the first 7 floating point elements in the call argument list are passed in registers:
                        - Non-FP Registers:  i0,i1,i2,i3,i4,i5,i6
                        - FP Registers:      f0,f1,f2,f3,f4,f5,f6
                        - It is the responsibility of the callee to narrow data passed through registers to the underlying data type if the passed data type is smaller than the word size. 
                        - Structures passed through registers are encoded identically to their in memory representation.  
                    - The first non floating point element and the first floating point element in the return argument list are passed in registers:
                        - Non-FP Register:  i7
                        - FP Register:      f7
                        - It is the responsibility of the caller to narrow data returned through registers to the underlying data type if the passed data type is smaller than the word size. 
                        - Pointer values and structures smaller or equal to the word size are in integer registers
                        - Structures passed through registers are encoded identically to their in memory representation. 
                    - Portions of the call argument list that don't fit in registers are pushed to the stack by the caller and popped from the stack bt the callee using the sized push/pop operations before the call instruction. 
                    - The return argument list always fits in registers.

        Globals: 
            Globals are stored in a fixed segment of the executable and relocated with the rest of the executable code. 
            This allows them to be accessed using PC relative addressing in a position independent executable.
